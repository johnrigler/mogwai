# Mogwai — User-Controlled Interactive Frame

**Concept note: 2026-09-11**

Mogwai is the interactive medium in the larger system. It is the screen-facing environment that a user enters after encountering a physical or ledger-linked object, especially through Dark Star.

Mogwai occupies some of the same behavioral territory as YouTube: moving images, audio, transcripts, navigation, playback, media selection, and interaction. The critical difference is that the user controls the frame.

Mogwai should not reproduce a recommendation feed that decides what the user should see next. It should resolve objects, expose their available representations, and let the user choose how deeply to enter external infrastructure.

## Position in the stack

```text
Dark Star      physical medium / passbook / ceremony
Mogwai         interactive medium / user-controlled frame
CertLedger     legal and institutional record layer
Chisel         transaction and encoding machinery
Ledgers/IPFS   persistence and content-addressed storage
```

Dark Star generally pushes the reader toward Mogwai as the default interactive environment. Mogwai then exposes the fact that it is only one possible reader. A technically curious user can descend below it into CIDs, transactions, block explorers, Chisel, raw protocols, or another viewer entirely.

Mogwai should be a particularly good frame, not a mandatory gateway.

## Two frames

Mogwai gives the user control over two different decisions.

### Content frame

What representation of an object should be presented?

```text
text
transcript
audio
reduced visual representation
full video
raw artifact
ledger record
```

### Network frame

Which infrastructure should be permitted to supply that representation?

```text
IPFS
YouTube
local cache
local file
ledger
other resolver
```

A future interface could make those choices explicit:

```text
VIEW

[ text ]
[ listen ]
[ reduced ]
[ original ]

SOURCE

[x] IPFS
[ ] YouTube
[ ] local
```

The user should be able to enter a work without automatically entering the behavioral environment of the platform that originally hosted it.

## YouTube is a source, not the object

Mogwai should treat a YouTube identifier as a locator for one representation of an information object, not as the permanent identity of the object itself.

A video uploaded to YouTube may in practice be several different kinds of information object:

```text
podcast              -> audio + image + transcript
static lecture       -> audio + slides + transcript
talking head         -> audio + transcript + sparse keyframes
screen demonstration -> audio + transcript + changed regions / clips
music video          -> preserve full video
film / animation     -> preserve full video
sports               -> generally preserve video
```

The useful question is not only:

> How efficiently can every frame be compressed?

It is also:

> Which changes in this media object actually carry new information?

This is semantic decomposition rather than ordinary codec compression.

## YouTube decomposition pipeline

A Mogwai ingestion process could look roughly like this:

```text
YouTube
   |
   v
[ acquire ]
   |
   v
[ analyze ]
   |
   +-- visual change
   +-- scene cuts
   +-- slide / text change
   +-- speech / transcript
   +-- audio characteristics
   |
   v
[ classify ]
   |
   +-- full video
   +-- segmented video
   +-- audio + keyframes
   +-- audio + static image
   +-- transcript
   |
   v
[ IPFS objects ]
   |
   v
[ Mogwai manifest ]
```

A two-hour YouTube upload showing one title image does not need to remain a two-hour video in every preserved representation. It can be represented as an audio object, a single image, and a transcript.

A slide lecture might become:

```text
source
  youtube:VIDEO_ID

derived
  transcript.txt
  audio.opus
  slide-0001.webp
  slide-0002.webp
  slide-0003.webp

timeline
  00:00 image:slide-0001.webp
  08:17 image:slide-0002.webp
  21:42 image:slide-0003.webp
```

The result is not claimed to be byte-for-byte restoration of the original upload. It is another representation of the same work.

## Fidelity levels

Different nodes and users should be able to preserve different levels of fidelity.

```text
L0  transcript
L1  transcript + representative still
L2  transcript + audio
L3  audio + semantic keyframes
L4  audio + keyframes + important video clips
L5  complete original video
```

A small IPFS node could preserve L0-L2 for a large number of works. An archival node could preserve L5. A Mogwai manifest describes the available constellation of representations.

## The manifest is the durable media description

The specific codecs and hosting platforms will change. The manifest should therefore be simpler and more durable than any single renderer.

A conceptual example:

```text
MOGWAI/1

SOURCE youtube:VIDEO_ID

AUDIO bafyAudio...
TEXT  bafyTranscript...

IMAGE bafyImageA... 0
IMAGE bafyImageB... 223
IMAGE bafyImageC... 557

VIDEO bafyClipA... 901 946
```

Each component is independently addressable. The object is a constellation rather than one monolithic media file.

Chisel or another ledger tool can anchor the manifest or a CID that identifies it. The media itself does not need to be written on-chain.

## YouTube without the YouTube environment

YouTube is useful infrastructure, but Mogwai should distinguish YouTube's transport from YouTube's behavioral environment.

The transport includes:

```text
video delivery
adaptive streaming
codecs
captions
global CDN
mobile playback
```

The environment includes:

```text
home feed
recommendations
Shorts
watch history
account profiling
advertising
notifications
engagement metrics
algorithmic sequencing
```

Mogwai can use the first without automatically adopting the second.

The preferred flow is:

```text
ledger or object reference
        ↓
Mogwai manifest
        ↓
specific media object
        ↓
YouTube / IPFS / local / transcript
```

The user arrives because one object pointed to another, not because a recommender predicted what would maximize continued viewing.

## Progressive independence from YouTube

A media object can gradually cease to depend on YouTube without requiring a dramatic platform migration.

```text
initial
  youtube

then
  youtube
  + transcript

then
  youtube
  + transcript
  + audio
  + keyframes

finally
  youtube        optional
  IPFS forms     sufficient
```

The objective is not to build a decentralized clone of YouTube. That would reproduce an enormous storage and distribution problem that is unnecessary for much of YouTube's actual informational content.

The objective is to make useful works independently understandable and preservable when that can be done lawfully and with appropriate permission or rights.

## Health and brittleness

YouTube health is not one Boolean value. Mogwai should distinguish at least:

```text
network reachability
iframe API availability
player initialization
specific video playability
embedding permission
regional accessibility
buffering and playback quality
API quota / metadata availability
```

A particular video can fail while YouTube is globally healthy. An API can fail while direct playback still works. A platform can be technically healthy while becoming undesirable as the default environment because of surveillance, recommendation pressure, login friction, policy changes, or account dependence.

Mogwai should expose those distinctions instead of collapsing them into "YouTube works" or "YouTube is down."

## Mogwai as observer

A Mogwai instance could eventually record signed observations of external media infrastructure:

```text
timestamp
video identifier
player-ready time
buffering
error code
approximate region
Mogwai version
```

Aggregated observations could become a distributed view of whether a media source is functioning for the people actually consuming it.

Mogwai would then be both viewer and observer.

## Algorithmic extraction

The deeper purpose is not simply media playback.

Mogwai can take an information object that currently lives inside an algorithmically controlled feed and place it into a user-directed object space.

That means the core operation is something like:

```text
platform object
      ↓
identify
      ↓
decompose
      ↓
address components
      ↓
preserve useful representations
      ↓
reassemble under user control
```

This is **algorithmic extraction**.

The user is not forced to inherit the original platform's recommendation machinery simply because the work was originally published there.

## Relationship to Dark Star

Dark Star is usually the physical onboarding medium. It teaches the grammar before Mogwai presents the interactive implementation.

A reader learns, implicitly:

```text
this symbol identifies something
this QR code resolves somewhere
this object may have several forms
this artifact may outlive this page
provenance can be inspected
following a link is a choice
```

Then:

```text
Dark Star
   ↓
QR / address / code
   ↓
Mogwai
   ↓
artifact
   ├── read
   ├── listen
   ├── watch
   ├── inspect provenance
   ├── inspect ledger
   └── interact
```

The literary Dark Star edition prepares a user to enter Mogwai. Other Dark Star editions can prepare users for other specialized destinations, including CertLedger.

## Relationship to Chisel

Mogwai should not absorb Chisel's job.

Chisel constructs, signs, encodes, and broadcasts transactions. Mogwai resolves and presents objects. They can share identifiers and protocols without sharing every implementation detail.

In the simplest terms:

```text
Dark Star teaches the grammar.
Mogwai is the default interactive reader.
Chisel exposes the machinery.
The underlying protocols remain independent.
```

That independence is intentional. If Mogwai became the only gateway, the system would merely replace one platform-controlled frame with another.
