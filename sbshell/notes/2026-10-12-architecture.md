# SB Shell / DAISY / Mogwai: architecture notes (2026-10-12)

Status: working notes, not a finalized specification. This file records the design discussion before any implementation changes.

## Boundaries

- **Mogwai** is the persistent tools and integration layer. It owns adapters for filesystems, ledger readers/writers, IPFS gateways/nodes, media conversion (for example FFmpeg), caching, and optional services. It may invoke **Chisel** to construct or inscribe transactions, but **does not require Chisel**. Other ledger tools can be substituted. Mogwai is not tied to any single ledger.
- **DAISY** is the chronological, filesystem-first body of records and artifacts. It groups material by year and other chronological coordinates. It can exist and be inspected without a running Mogwai process. SB Stats and legal/CertLedger work can use the same underlying format.
- **SB Shell** is the editorial, navigable, printable reading layer over files and DAISY records. Its purpose is to tell a story, not to duplicate the source archive. Dark Star material may be linked or incorporated in SB Shell issues.
- **Chisel** is an optional transaction construction, signing, broadcast and inscription tool, not the sole ledger interface.
- **FileProxy** is an optional local filesystem service. Neither static publication nor the underlying DAISY records should require it.
- **IPFS** is an addressable content transport/publication substrate. Place gateway/node interaction and content resolution in Mogwai, while allowing DAISY, SB Shell, Chisel, and other clients to refer to CIDs.

## Existing SB Shell behavior to preserve

- Left/right navigation between editorial pages or ordered units.
- A selected unit is a potentially long HTML page composed of separately numbered parts: HTML fragments, image files (for example PNG), and references to material stored elsewhere.
- The source directory may mix regular files, subdirectories, and Unix symlinks. Numbered names encode deliberate presentation order; the content need not be duplicated to be included.
- Web presentation and US Letter (8.5 x 11 inch) portrait/landscape printing are alternative renderings of the same editorial sequence.
- Keep Bash, vi, and the filesystem as first-class authoring surfaces; vanilla JavaScript is sufficient for the static browser renderer. PHP and Python can be optional adapters, not mandatory runtime dependencies.

## Proposed resolution model (not yet implemented)

The numbered entry should describe **placement in the story**, independently of **where bytes are stored**. A resolver could support:

1. A regular local file.
2. A local symlink to a file/directory.
3. An IPFS CID or HTTP gateway URL.
4. An SSHFS-mounted file or other local mount, when explicitly configured.
5. A ledger reference, such as chain + block hash/height + transaction ID + byte-range or recognized inscription.
6. A generated/transformed asset made by an external tool such as FFmpeg.

Resolution should make immutable, content-addressed **materializations** where practical: record the logical source reference, exact bytes/hash, length, MIME type, retrieval method, tool version, and provenance. Reuse verified cached bytes on subsequent reads. The published static/IPFS export should include real byte streams or immutable links rather than assume that Unix symlinks or SSH mounts will resolve in a browser.

**Devices are not normal source documents:** `/dev/null` gives an empty stream, `/dev/zero` is effectively unbounded. A future resolver must block or explicitly bound special-device reads, prevent recursive links and directory escapes, cap output sizes/time, and never blindly copy or publish such targets. An ordinary browser must not be allowed to request arbitrary local paths.

## BSV / blk-file exploration: related but separate research track

Hypothesis: A canonical **active-chain index** could identify blocks by height/hash while the underlying block bytes are scattered among local files, removable media, remote mounts, or content-addressed chunks. A Chromebook-scale **read-only explorer with lazy verified fetch and bounded cache** is a plausible target. Whether a fully validating BSV node could work on that model is **not established**.

Important distinction:
- A `blk*.dat` file may hold blocks in network reception/storage order, **not necessarily chain-height order**.
- **Transactions within a serialized block already have a committed order**: the Merkle root depends on it. They cannot be reordered into a 'better' canonical sequence without changing the block. Canonical *block chain order* is a separate question from transaction order *within each block*.
- An active-chain sequence requires consensus/fork-choice validation, not simply sorting files by a filename or height string.
- A partial local cache is not by itself a full node. Full validation requires suitable consensus rules, historical verification or a separately verified state commitment, UTXO state, and handling forks/reorganizations. Separate *explorer*, *proof-verifying light client*, and *fully validating node* as different capability targets.

Research tasks: identify BSV node version/storage formats, block header and raw-block sources, proof formats and trust model, reorg behavior, chunk indexing, disk/network budgets, and cache eviction. Preserve original block serialization exactly.

2. Inspect and test current SB Shell rendering of mixed numbered regular files/symlinks with the root `files.txt` convention.
3. Define a small source-reference schema and secure resolver/cache contract in Mogwai; start with ordinary files and IPFS CIDs.
4. Add publication/export tests: static HTML/IPFS render, long-page layout, letter portrait and landscape printing.
